本次已完成内容
1. 明确后端范围
- 负责个人作品网站的后端和后台能力。
- 网站公开访问，仅有一个管理员。
- 不做多管理员、不做注册、不做分类和搜索。

2. 确定整体后端方案
- 推荐基线：PostgreSQL + 对象存储（图片、PDF、简历）+ 单管理员 Session/Cookie 登录 + REST API。
- 目标是尽量简单、稳定、方便后续持续新增作品。

3. 数据模型设计
- admin_users：单管理员账号表。
- admin_sessions：管理员登录会话表。
- site_profiles：首页基础信息表，仅保留一条记录。
- site_contact_items：联系方式列表表。
- assets：统一文件资源表，管理图片、项目 PDF、简历等上传文件。
- projects：作品主表。
- project_images：作品多图表，支持截图说明和排序。
- project_links：作品外链表，支持多个链接和排序。

4. 作品字段设计
- 每个作品支持以下内容：
  - 封面
  - 标题
  - 简介
  - 项目时间
  - 多图
  - 截图说明
  - PDF 预览文件
  - 多个外链
  - 手动排序

5. 首页信息设计
- 支持管理员修改：
  - 姓名
  - 一句话介绍
  - 联系方式

6. 简历能力设计
- 支持简历上传、预览、下载。
- 当前简历建议通过 site_profiles 关联 assets 表中的一份文件。

7. API 规划
- 公开接口：
  - GET /api/public/bootstrap
  - GET /api/public/projects
  - GET /api/public/projects/:slug
  - GET /api/public/resume
- 管理员认证接口：
  - POST /api/admin/auth/login
  - POST /api/admin/auth/logout
  - GET /api/admin/auth/me
- 后台管理接口：
  - GET /api/admin/site
  - PATCH /api/admin/site
  - PUT /api/admin/resume
  - GET /api/admin/projects
  - POST /api/admin/projects
  - GET /api/admin/projects/:id
  - PATCH /api/admin/projects/:id
  - DELETE /api/admin/projects/:id
  - PUT /api/admin/projects/sort
  - POST /api/admin/assets/image
  - POST /api/admin/assets/pdf

8. 文件上传方案
- 开发环境可先落本地 uploads 目录。
- 正式环境建议使用对象存储。
- 数据库只保存文件元数据，不直接保存文件二进制。
- 图片、项目 PDF、简历统一进入 assets 表管理。
- 上传时校验文件类型、大小、MIME、扩展名，文件名使用随机值避免冲突。

9. 登录与安全方案
- 不做注册，只保留单管理员账号。
- 登录建议采用服务端 Session + HttpOnly Cookie。
- 密码采用安全哈希存储（Argon2id 或 bcrypt）。
- 后台写接口统一校验登录态。
- 增加限流、来源限制、CSRF 防护、基础安全中间件。

10. 手动排序方案
- projects.sort_order 使用整数值。
- 前台和后台列表均按 sort_order 升序读取。
- 新建作品默认取最大值后递增。
- 后台拖拽后走批量排序接口，由后端统一重写排序值。

11. 部署建议
- 前台静态部署，后台 API 独立部署。
- 数据库使用 PostgreSQL。
- 文件使用对象存储。
- 若主要面向中国大陆访问，优先考虑阿里云或腾讯云体系。
- 若主要考虑全球访问和成本，可考虑 Cloudflare 相关方案。

12. 前端配合要求
- 前端不要把首页信息、作品信息、简历信息写死在代码里。
- 统一从公开 API 获取最新数据。
- 上传类表单建议先上传文件，拿到 assetId 后再提交业务数据。
- 图片、PDF、简历统一使用后端返回的 URL，不由前端自行拼接路径。
