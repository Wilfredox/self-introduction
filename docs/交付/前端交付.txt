3. 首页缩放/拖动交互技术方案
- 首页拼贴区不建议使用真实 canvas 绘制卡片
- 采用 DOM 卡片 + 单一 transform 舞台方案
- 所有作品卡片在舞台内使用绝对定位
- 舞台统一使用 translate3d(x, y, 0) scale(scale) 控制缩放和平移
- 交互状态建议独立维护：
  viewState = { x, y, scale, activeProjectSlug }
- 鼠标滚轮缩放采用“以光标为中心缩放”
- 拖动画布采用 Pointer Events
- 点击与拖动之间要设置阈值，避免误触
- 高频位移和缩放更新建议使用 requestAnimationFrame
- 移动端和平板仅让拼贴舞台区域接管手势，避免整页滚动冲突
- 点击作品卡片后，不离开首页，而是在首页内拉起放大简介层
- 放大态第一行展示作品链接，下面展示简介和入口操作
- 放大态建议同步到 URL 查询参数，支持刷新恢复和分享
- 需要提供“重置视图”能力，避免用户拖离主要内容区域

6. 风险点与需要后端配合的地方
- 首页缩放拖动与移动端滚动手势可能冲突
- 后台更新后前台“及时响应”需要后端提供 contentVersion 或聚合 updatedAt
- PDF 在线预览需要后端或对象存储支持稳定访问、CORS、Range 请求
- 图片最好区分缩略图和原图，避免首页直接加载大图
- 手动排序需要后端提供稳定持久化接口
- 后台登录建议采用 HttpOnly Cookie 会话方案
- slug 需要保证唯一
- 作品需要 draft/published 状态，避免未完成内容直接对外暴露

3. 本轮这样做的原因

1) 先上正式脚手架
因为第二轮要求已经从“确认方向”进入“执行落地”，继续只维护静态 HTML 原型已经不适合后续联调和持续新增作品。

2) 先做统一 mock 数据层
因为后端接口第一版还在同步推进，前端必须先用统一 mock 数据把页面结构和交互跑通，后续才能平滑替换为真实 API。

3) 首页交互和内容状态分离
首页缩放、拖动、聚焦态属于前端视图状态；作品标题、简介、链接、截图说明属于内容数据。两者分离后，后续换设计稿或换接口都更稳。

4) 后台修改联动前台
本轮已通过 localStorage + 统一数据更新事件模拟“后台改完，前台能拿到最新内容”的链路，为真实接口联调提前铺好结构。

1) 产品字段仍有缺口
当前统一内容模型里：
- ProjectLink 缺少 projectId
- ProjectImage 缺少 projectId
如果后端最终 schema 不补关联字段，前端无法稳定做项目级外链和截图管理。

3) 首页自由拼贴位置目前仍是前端预设
本轮按 sortOrder + 前端预设槽位完成 A 版首页。
如果后续希望管理员手动控制每张卡片在首页中的具体位置、角度和尺寸，需要新增布局字段。

当前正式前端使用的是路由模式，不是多 HTML 页面模式。
