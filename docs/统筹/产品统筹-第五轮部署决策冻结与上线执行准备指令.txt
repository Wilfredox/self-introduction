产品统筹 - 第五轮部署决策冻结与上线执行准备指令
更新时间：2026-04-26

一、当前判断

项目现在已经不是“继续开发功能”的阶段了。

当前主干状态：
1. 前端已能构建
2. 后端已能构建
3. 公开页与后台链路已跑通
4. 后台可继续承接你后续补真实内容
5. 当前最大阻塞已经从“代码未完成”切换为“部署路线未冻结、正式环境未落地”

因此，第五轮的目标不是扩需求，也不是继续做视觉方向讨论，而是：
冻结部署路径，准备实际技术上线执行

二、本轮冻结的推荐部署路线

如果没有额外预算、团队也不想现在扩运维复杂度，本轮统一按下面这条路线准备：

推荐路线（V1 技术上线版）：
1. 一个正式域名
2. 一台 Linux 服务器或等价平台容器
3. 前端静态站点部署在同一域名下
4. 后端 Node 服务运行在服务器内网端口
5. 通过反向代理统一暴露：
   - `/api`
   - `/uploads`
6. 使用 PostgreSQL
7. 技术上线第一版先允许继续使用服务器本地磁盘上传
8. 暂不在本轮引入对象存储、跨域前后端拆分、Docker 编排、多环境灰度等额外复杂度

当前冻结的访问形态：
- 网站：`https://your-domain.com`
- API：`https://your-domain.com/api`
- 上传资源：`https://your-domain.com/uploads/...`

说明：
1. 这条路线和当前前端 `/api` 相对路径方案完全一致
2. 这条路线和当前后端 Cookie Session 方案也最匹配
3. 它不是最终最强运维方案，但它是当前最稳、最省沟通成本、最适合先技术上线的路线

三、本轮明确不做的事

第五轮不要做：
1. 不新开页面
2. 不改产品范围
3. 不改首页方向
4. 不做跨域前后端拆分
5. 不把上传方案临时升级成对象存储，除非部署负责人明确要求
6. 不引入 Docker / K8s / CI/CD 流水线作为当前轮次前置条件

说明：
这些事以后都能做，但现在它们会拖慢真正上线。

四、第五轮总目标

本轮只做 4 件事：
1. 冻结正式部署路径
2. 补齐部署所需文档和执行信息
3. 明确正式环境变量和基础设施准备项
4. 形成“可以开始真正部署”的上线执行包

五、第五轮分工

[A] UI 设计

本轮角色：
上线前视觉签收配合

本轮必须完成：
1. 不再新增设计稿
2. 不再起新方向
3. 仅保留一份“上线后第一轮视觉复核清单”
   至少覆盖：
   - 首页首屏
   - 首页放大态
   - 作品详情页 PDF 容器
   - 简历页预览区
   - 后台登录页
   - 后台管理页

4. 在 `docs/交付/UI设计交付.txt` 中补一段：
   - 第五轮上线前视觉签收结论
   - 上线后必须再看一次的页面
   - 哪些问题不阻塞技术上线，但会影响正式公开展示气质

UI 本轮通过标准：
1. 不再新增设计任务
2. 输出一份清楚的上线后复核清单
3. 明确哪些是“技术上线可接受”，哪些是“公开前建议继续收”

[B] 前端开发

本轮角色：
正式部署前前端交付收口

本轮必须完成：
1. 确认正式前端构建产物可直接用于部署
2. 整理前端部署说明
   至少写清楚：
   - 生产环境构建命令
   - 部署后前端静态文件目录要求
   - 浏览器路由回退到 `index.html` 的要求
   - 前端依赖 `/api` 同域代理的前提
   - 前端是否还依赖任何本地开发专用配置

3. 再做一轮上线前前端清查
   至少确认：
   - 前端正式源码中没有 localhost API 默认回退
   - 前端正式源码中没有演示密码
   - 前端关键页不会因为空内容 / 占位内容直接崩溃

4. 在 `docs/交付/前端交付.txt` 中补一段：
   - 第五轮前端部署准备结果
   - 正式部署前端需要什么
   - 部署后最小前端 smoke check 清单
   - 仍建议人工手测的交互点

前端本轮通过标准：
1. 能清楚告诉部署执行人“前端怎么放上服务器”
2. build 持续通过
3. 没有新的明显发布阻塞

[C] 后端开发

本轮角色：
正式部署执行信息收口

本轮必须完成：
1. 将当前后端部署文档继续收成“可执行版本”
   至少保证下面这几项清楚可用：
   - `production-deploy-checklist.md`
   - `technical-launch-runbook.md`

2. 明确正式环境变量模板
   如果当前还没有足够清楚的正式模板，建议补：
   - `backend/.env.production.example`
   或在现有文档中给出完整正式样例

3. 明确正式部署顺序
   至少覆盖：
   - 安装依赖
   - Prisma generate
   - migrate deploy
   - seed
   - build
   - start
   - `/api` 和 `/uploads` 代理

4. 明确正式环境仍未替换的内容
   至少列清楚：
   - 正式 PostgreSQL
   - 正式域名
   - 正式管理员密码
   - 正式上传存储策略

5. 在 `docs/交付/后端交付.txt` 中补一段：
   - 第五轮后端部署执行准备结果
   - 现在是否已经达到“可开始部署”
   - 真正部署前最后还缺什么

后端本轮通过标准：
1. 后端部署步骤已清楚到可以交给执行人照着做
2. build 持续通过
3. 正式环境阻塞项已被明确列出，而不是模糊挂起

六、你本人当前需要准备的决策

这一轮你不一定要马上提供真实内容，但你需要准备以下 4 个部署决策：

1. 正式域名
2. 服务器 / 平台
3. PostgreSQL 准备方式
4. 上传文件第一版是否接受“服务器本地磁盘”

我给你的推荐口径是：
1. 域名：一个主域名即可
2. 服务器：一台 Linux 服务器即可
3. PostgreSQL：能独立用就独立用；如果暂时没有，至少要确保正式数据库不是当前 Prisma Dev 临时库
4. 上传：第一版先接受服务器本地磁盘，后续再升级对象存储

七、本轮完成后的理想状态

第五轮完成后，项目应该达到：
1. 路线不再摇摆
2. 部署执行人知道要怎么上
3. 三方都知道自己上线前最后要交什么
4. 你只差准备正式域名 / 服务器 / 数据库，就可以开始真实部署

“项目进入第五轮：部署决策冻结与上线执行准备阶段。本轮不再扩需求，不再开新方向，统一按‘同域部署 + /api + /uploads + PostgreSQL + 服务器本地上传作为 V1 技术上线方案’推进。请按《docs/统筹/产品统筹-第五轮部署决策冻结与上线执行准备指令.txt》补齐各自的部署准备结果，并把本轮新增内容、部署说明、剩余阻塞和需要我决策的事项写回各自交付记录。”
