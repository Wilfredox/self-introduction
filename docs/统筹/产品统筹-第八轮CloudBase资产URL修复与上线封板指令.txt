产品统筹 - 第八轮 CloudBase 资产 URL 修复与上线封板指令
更新时间：2026-04-26

一、当前判断

第七轮整体已经把 CloudBase 路线落进了代码主干：

1. 运行时配置已支持 `cloudbase`
2. 存储 dispatch 已支持 `cloudbase`
3. CloudBase HTTP 入口已经出现
4. 前后端 build 继续通过

这说明项目已经不再卡在“路线是否存在”。

现在真正挡住快速上线的，只剩一个需要先修掉的风险：

CloudBase 上传后，把 `getTempFileURL(...)` 返回的访问地址直接写进数据库，
后续公开接口再把这个历史 URL 原样返回。

这会导致一个真实问题：

如果当前文件并不是永久公开读，或者未来权限策略变化，
已经上传过的封面图、项目 PDF、简历 PDF 就可能因为临时 URL 过期而失效。

因此第八轮不再扩需求，不再讨论新平台，不再重开设计。

第八轮目标只有一个：

把 CloudBase 资产访问链路修成“可上线封板”的状态。

二、第八轮总目标

本轮只做 3 件事：

1. 停止把 CloudBase 临时访问 URL 当成数据库中的长期正式 URL
2. 保持前端现有资源字段口径不变：
   - `url`
   - `previewUrl`
   - `downloadUrl`
3. 完成最小上线前 smoke check，确认首页、详情页、简历页、后台上传链路不被这次修复打散

三、第八轮默认修复路线

为了尽快上线，本轮默认采用：

`持久化 fileID / objectKey，读时生成当前可访问 URL`

原因：

1. 这是当前代码基础上改动最小、风险最可控的修法
2. 不需要这一轮同时引入新的公开域名策略
3. 不要求这轮重做前端字段结构
4. 能优先保证“旧资源不因为历史临时链接过期而失效”

本轮不默认采用：

`直接把 CloudBase 永久公开 URL 方案做死`

原因：

1. 这件事通常会继续牵涉：
   - 存储权限
   - 默认访问域名
   - 公开读策略
   - 后续正式域名规划
2. 现在项目目标是“尽快上线”，不是在这一轮把长期资源架构一次做满

后续如果确认 CloudBase 资源全部走明确永久公开策略，
可以再把“读时生成 URL”优化掉，但这不是第八轮封板前必须完成的工作。

四、第八轮分工

[A] UI 设计

本轮角色：
待命 + 上线前视觉复核配合

本轮必须完成：
1. 不新增设计稿
2. 不改页面结构
3. 仅在 `docs/交付/UI设计交付.txt` 补一句状态说明：
   - 第八轮 UI 无新增设计改动，等待资源链路修复后配合做图片 / PDF / 简历预览复核

UI 本轮通过标准：
1. 不新开设计需求
2. 明确当前关注点只剩资源是否正常显示

[B] 前端开发

本轮角色：
保持页面层稳定，配合验证修复后的资产 URL 链路

本轮必须完成：
1. 不重做页面
2. 不改产品字段
3. 不引入平台 SDK 到前端页面层
4. 重点检查以下依赖资源 URL 的位置：
   - 首页封面图
   - 作品列表封面图
   - 作品详情封面图 / 多图 / PDF 预览
   - 简历页 PDF 预览 / 下载
   - 后台上传后的即时回显

5. 如果后端修复后仍保持：
   - `url`
   - `previewUrl`
   - `downloadUrl`
字段不变，则前端本轮原则上不改页面代码

6. 本轮必须在 `docs/交付/前端交付.txt` 中补一段：
   - 第八轮前端是否改了代码
   - 如果没改，写清楚原因
   - smoke check 重点检查了哪些资源承载点
   - 是否发现刷新、预览、下载异常

前端本轮通过标准：
1. 页面层继续稳定
2. build 继续通过
3. 在资源字段不变前提下，不做无意义大改

[C] 后端开发

本轮角色：
第八轮封板主负责人

本轮必须完成：

1. 修正 CloudBase 资产持久化策略
目标：
- 不再把 `getTempFileURL(...)` 返回值直接作为资产长期正式 URL 持久化
- 数据库中的长期识别依据应继续以：
  - `storageProvider`
  - `objectKey` / `fileID`
为主

说明：
- 本轮不要求推翻当前 `assets` 表
- 但必须停止把“可能带临时语义的访问地址”当成长期稳定真值写死

2. 改成读时生成当前可访问 URL
目标：
- 在公开接口和后台读取资产时，
  如果 `storageProvider=cloudbase`，
  应基于 `objectKey` / `fileID` 生成当前有效访问地址
- 重点覆盖：
  - 首页聚合接口
  - 作品列表接口
  - 作品详情接口
  - 简历接口
  - 上传成功后的返回结构

说明：
- 如果当前 `resolveAssetUrls` 是同步函数，本轮允许改成异步链路
- 但不要为了这一轮封板去推翻整个 service 结构

3. 前端字段口径不得被打散
目标：
- 修复后仍继续返回：
  - `url`
  - `previewUrl`
  - `downloadUrl`
- 不把这轮修复变成前端接口重构

4. 明确旧数据怎么处理
目标：
- 写清楚当前数据库里如果已经存在历史 CloudBase 临时 URL，
  本轮读取时是否会被新的读时生成逻辑覆盖
- 如果会覆盖，说明“无需额外数据迁移”
- 如果不会覆盖，必须明确：
  - 是否需要一次性修复脚本
  - 还是清空测试数据后重传

要求：
- 这个结论必须写进 `docs/交付/后端交付.txt`

5. 文档口径补清楚
目标：
- `backend/README.md`
- `backend/docs/production-deploy-checklist.md`
- `backend/docs/technical-launch-runbook.md`
至少要补一句清楚说明：
  - 当前 CloudBase 资源访问链路采用“持久化 fileID，读时生成访问 URL”策略

6. 本轮必须完成最小验证
至少说明是否完成了以下验证：
- 上传图片后立即读取返回结构
- 上传 PDF 后详情页预览 URL 是否存在
- 简历资源读取是否存在 `downloadUrl`
- 前后端 build 是否继续通过

后端本轮通过标准：
1. CloudBase 临时 URL 不再被当成长期正式 URL 写死
2. 公开读取链路能基于 `objectKey` / `fileID` 给出当前可访问地址
3. 不打散前端已有字段口径
4. 文档和交付记录已同步

五、本轮禁止事项

第八轮不要做：

1. 不新增产品功能
2. 不改首页结构
3. 不重做后台
4. 不重新讨论 Render / Supabase 路线
5. 不顺手重构整个后端存储系统
6. 不把这轮修复扩成“长期资源架构大改造”

六、第八轮完成后的理想状态

如果第八轮完成得好，项目应达到：

1. CloudBase 路线不存在明显的“旧资源未来失效”风险
2. 前端资源展示链路继续稳定
3. 图片 / 项目 PDF / 简历 PDF 的访问策略可承受技术上线
4. 下一步就可以直接进入：
   - 真实 CloudBase 环境实配
   - 真实上传
   - 真实访问 smoke check
   - 技术上线执行
